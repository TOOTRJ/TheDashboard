## Authorized cutover sequence and acceptance

1. **Prepare both sides before clearing the legacy pointer.** The official migration preview is read-only; `migrate --apply` writes a local file and clears the remote Config File setting. That clear is a consequential operation before normal IaC planning and is not the IaC apply. Prefer a separately reviewed exact-service pointer clear only if Railway presents it as a scoped stage with no unintended deploy, the equivalent dashboard fallbacks are proved, and the rollback route is ready. Railway's UI supports committing supported staged settings without redeploy; verify it for this field. If the field was unset, do not manufacture a change. An IaC plan may still refuse until legacy management is cleared: record the refusal, and stop if the clear would require an unreviewed deployment or cannot be verified on the same ID. Never bypass the guard with a second service. [Migration procedure](https://docs.railway.com/infrastructure-as-code#migrating-from-config-as-code) · [Railway staged changes](https://docs.railway.com/deployments/staged-changes).
2. **Plan after the legacy guard is cleared.** Refresh target, ownership and stage state. Evaluate just the reviewed partial; require the admitted diff above and no other pending deploy. Pin the exact environment `configEtag` and authoring tree if the isolated CLI supports a saved plan. Keep that plan private, and verify what it contains without printing secrets. A changed etag/tree means re-plan and review, never force. In an interactive flow, inspect the fresh apply plan against the reviewed one before confirming; `apply --json` can execute without prompting, and a destructive override has no place in this migration. Treat a partial claim as a mutation even if the plan has no settings delta. [Plan pinning and apply flags](https://docs.railway.com/cli/config#apply-changes).
3. **Do only one deliberate closed deployment for acceptance.** First verify whether apply itself schedules a deploy, and whether it would use the exact approved artifact and equivalent settings. If it does, that deploy must be reviewed as the single closed candidate before apply. Otherwise do the explicit scoped upload after the setting apply, with the verified cutover manifest and no legacy file. Do not assume the old image or a config success means the IaC-based deploy is accepted. Serialize any apply/upload; after a lost reply check the exact service state and original deployment before any retry.
4. **Verify the same service from artifact to runtime.** Capture the new deployment ID, resolved config source and image/source identity; confirm all settings and limits match, no legacy override is used, and the service remains closed. Read-only checks: `/health` returns `200`; anonymous `/v5/status` returns `401`; a forbidden Origin returns `403`; `/colonies` and `/docs` return `404`; expected `Cache-Control: no-store` headers hold. An authorized Dashboard Auth identity should receive the expected closed `503` on `/v5/status`. Verify fixed-host CA/hostname TLS/IPv6 without database login or economic writes. Verify no new provider/native/operator credentials and no worker admission. Do not count old probe results as fresh evidence. Record only sanitized checks; no claims about full hosted native Auth, database migration, B2 adoption or paper pilot acceptance follow from HOST-02C.

## Undo and stop rules

- **Before commit:** discard only the worker's own staged change. If the legacy pointer was cleared but IaC was not applied, restore only its exact verified preimage if still supported and necessary; otherwise retain the known closed runtime and repair the persisted settings. Avoid a deploy during reversal unless required and reviewed.
- **After IaC apply:** prefer a reviewed inverse against the current etag and the same service/ownership, restoring the recorded effective settings. If undo requires removing the ownership claim, explicitly dry-run release of only the verified service address, then use the exact preview/etag with existing environment-admin authority and reverify. Removing the declaration and applying it can delete the owned service. Ownership release does not restore settings or deployment. Do not reapply a released partial accidentally. [Railway ownership release semantics](https://docs.railway.com/cli/config#release-ownership).
- **After an unhealthy or uncertain deployment:** stop further applies, uploads and admission, observe the exact original result, and abort only the known in-progress candidate where appropriate. If eligible, use the verified closed rollback target; Railway rollback restores both its image and custom variables, and plan retention can remove that option. Never select an older provider/native credential-bearing deployment. If unavailable, use the prepared exact closed export with equivalent persisted configuration on the existing service. After December 1, restoring a legacy file is not a configuration rollback; use the inverse persisted settings and safe closed artifact instead. Confirm identity, mode, Auth/TLS and read-only health again. [Deployment rollback, retention and cancellation](https://docs.railway.com/deployments/deployment-actions#rollback).

Do not claim HOST-02C complete until the exact-source plan, applied settings, independent review, closed deployment checks and documented safe rollback agree.
